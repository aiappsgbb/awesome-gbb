# Output acceptance scenarios

These are **unexecuted, synthetic guardrail probes**, not user research or proof
of quality. They supplement, never replace, the user's real disappointing case.
Static contract tests checking this file do not execute these scenarios.

## Run protocol

Use an isolated project/local scope with the source `SKILL.md` and its references.
Follow the host's supported loading mechanism and record discovery and invocation
separately. Do not install globally or overwrite a personal skill for the test.

For each case:

1. Record runtime/model, skill source revision/hash, tools, brief and write scope.
2. Have the agent apply the skill to the task, not just summarize its instructions.
3. Review the real-content wireframe and explicitly approve a structure before build.
4. Capture the resulting files, desktop/mobile behavior and task evidence.
5. Report observed, source-inferred, not checked and blocked results; get owner
   acceptance before claiming the case succeeded.

Do not start paid services or external generation for these fixtures. If the
host cannot render or exercise a required path, record it as unverified.

## Case 1: executive report

**Goal:** create a consultable report supporting a choice, with a distinct complete
print view and a single-file offline delivery. Do not force readers through the
whole document to find the recommendation.

**Supplied synthetic material:**

| Option | Cost units | Lead time | Evidence |
|---|---|---|---|
| A | 30 | 2 weeks | S1: observed in a small synthetic trial; long-run behavior unknown |
| B | 18 | 5 weeks | S2: estimate only; no observed trial |
| C | Unknown | 3 weeks | S3: lead-time estimate; cost not supplied |

Recommendation supplied by the brief: A if the two-week deadline is binding;
B remains an alternative if five weeks is acceptable. No measured ROI or
production-readiness claim is authorized.

Provide source views S1-S3 from the notes above, clearly labeled synthetic.
They are not external citations. Preserve the unknown cost for C.

**Tasks:** find the conditional recommendation; compare A and B on both criteria;
open S2 and return; reopen a direct link to C; print and open offline.

**Required evidence:** conditions remain visible with the recommendation; comparison
does not depend on recalling another tab; all sources and C appear in the complete
print output; no network dependency or broken `file://` route; no invented cost.

## Case 2: comparison and consultation tool

**Goal:** inspect and return to filtered records without confusing availability
with verified evidence. Use a different structure from the report when the task
requires it; do not change just the palette.

**Supplied synthetic dataset:**

| Record | Group | Interface | Evidence |
|---|---|---|---|
| Intake review | Service | Available | Historical only |
| Return recommendation | Service | Available | Historical only |
| Shift briefing | Operations | Not available | Historical only |
| Asset inspection summary | Operations | Not available | None supplied |
| Policy comparison with a deliberately long descriptive title | Analysis | Not available | Historical only |
| Document classification | Analysis | Not available | None supplied |

No record has current owner acceptance. Available means an interface exists,
not that a demonstration or business action is authorized.

**Tasks:** filter Operations; find Shift briefing; inspect its evidence; switch
reader perspective and return; reload a shared detail URL; try an unmatched query.

**Required evidence:** query, group, collection and selection survive every relevant
return path; direct-link reload works; zero-result guidance addresses the actual
query/filter; no fake launch buttons; long titles remain readable; no "verified"
badge inferred from interface availability.

**Adversarial variant:** put the same audience switch in the header and in the
detail footer. Both must preserve the same context. A test of only the first
link is insufficient.

## Case 3: informational site with an existing identity

**Goal:** help visitors choose a workshop and understand attendance requirements.
Preserve the supplied identity rather than inheriting the report/tool layout.

**Brand constraints:** light surface, dark navy text, orange used sparingly for
actions, one readable sans family, rounded controls already established.
Do not replace it with a beige editorial theme or a dashboard shell.

**Supplied synthetic content:**

| Workshop | Format | Duration | Requirement |
|---|---|---|---|
| Introduction | In person | 45 minutes | No prior experience |
| Guided practice | Remote | 90 minutes | Introduction or equivalent experience |
| Open questions | Remote | 30 minutes | Bring a question; no registration system supplied |

There are no supplied dates, prices, testimonials, sponsors or booking backend.
Do not invent them or create a working-looking registration button.

**Tasks:** find a beginner session; identify the remote prerequisite; share that
requirement directly; navigate on mobile and by keyboard; use reduced motion.

**Required evidence:** appropriate structure for a small informational site; clear
format/duration distinctions; preserved brand; honest lack of registration;
navigation with recognizable labels; meaningful icons/motion where useful, no
required external imagery.

## Promotion decision

Record each case independently, including defects and tool limitations. Passing
one case does not certify all modes. Require the three classes, user acceptance
and the real baseline comparison before global promotion. If cost or scope grows,
agree the next bounded run instead of generating more examples automatically.
